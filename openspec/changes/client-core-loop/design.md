# Design: client-core-loop

## Context

现有 `JinliMain` 单组件每帧重画灰底、圆点与 9 个 Label。快照已包含阶段、双方状态、双榜和结算，Effect 已包含礼物归因与高光事件，无需扩充 core 协议。目标是在 Cocos Creator 3.8.8、零新增依赖和既有性能预算内形成可辨识、可持续观看的国潮演出。

## Decisions

### CV1：采用「流光国潮」原创美术与动态舞台

黛青山水为底，朱红与青蓝区分阵营，鎏金只用于仪式和高光。原创 SVG 生成 PNG 山水、珠光锦鲤、鎏金龙门与琉璃面板，配合现代 CJK 字体；水波和粒子保留轻量 Graphics。视觉锚点是「双方鱼群沿灯河会跃龙门」，不是通用仪表盘。美术源文件与生成脚本入库，可重复生成，不依赖外部付费服务。

### CV2：视图拆为数据、场景与演出三层

- `ViewModel`：继续过滤文案，并维护有界、带过期时间的 `visualEvents`。
- `KoiRenderer`：负责 Cocos 节点、静态背景、Sprite 对象池、动态绘制、文本和对象上限；`art.ts` 统一加载原创美术与字体。
- `JinliMain`：只负责档案加载、数据源、时钟和逐帧委托。

### CV3：事件反馈按强度分级

点赞/弹幕只产生局部涟漪和短反馈；礼物按档位产生鱼群、印章和个人推进归因；充能、克制、逆流改变河道氛围；跃龙门和结算使用短时全屏仪式。普通事件不得长期遮挡规则与进度。

### CV4：布局与性能先有护栏

继续使用 Layout Profile 和安全区；修复 feed 与规则区重叠。每方鱼形 ≤32，粒子 ≤48，visualEvents ≤24，feed ≤4，推进飘字 ≤8。64 个鱼形 Sprite 与 8 个飘字 Label 仅启动时创建并复用；静态层仅构建时绘制，文本仅赋值，不新增运行时资源。鱼群持续游动/摆尾，实际进度增加触发短冲刺。

### CV5：真实流量结论必须靠实验

本变更提供参与率、停留与破冰所需的呈现基础，但不承诺 UI 本身带来流量。H1/H2/H3 仍按 Goal 的单变量、最低样本量实验验证。

## Risks / Trade-offs

- 程序化图形不及精修立绘 → 先保证统一风格、清晰层级和演出节奏，后续可逐层替换 Sprite 而不改 ViewModel。
- 动效增加过绘 → 静态/动态分层、硬上限和真实 30 分钟复测。
- 多事件同时到达 → visualEvents  capped、短时 TTL，高优先级仪式覆盖低优先级反馈。

## Migration Plan

保留 `JinliMain` 公共属性、demo/net 数据源和既有 Profile 名称。旧场景无需修改；若新渲染异常，可回滚本变更的呈现文件，不影响服务端协议。
